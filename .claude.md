# Zoi AI Ecosystem - AI Development Agent Context

> **This file provides comprehensive context for AI development agents (Claude, Augment, GitHub Copilot, etc.) to understand the Zoi ecosystem architecture, conventions, and best practices.**

## 🎯 Project Overview

**Zoi** is a production-ready, self-hosted AI ecosystem built with Docker Compose microservices architecture. It provides unified AI model access, vector storage, workflow automation, and knowledge management.

### Core Philosophy
- **Self-Hosted First** - Complete control over AI infrastructure
- **Microservices Architecture** - Modular, scalable, maintainable
- **Configuration as Code** - Centralized, version-controlled configs
- **Developer Experience** - Easy setup, clear documentation, automation

## 🏗️ Architecture Overview

### Stack Organization
```
zoi/
├── apps/                    # Microservice stacks
│   ├── core/               # AI infrastructure (LiteLLM, vLLM, Ollama, Qdrant)
│   ├── platform/           # Base services (Traefik, Authentik, DBs)
│   ├── tools/              # Productivity (n8n, OpenWebUI, LobeChat)
│   ├── archon-mcp/         # Knowledge management
│   └── monitor/            # Observability
├── config/                 # Centralized configuration
├── scripts/               # Automation and utilities
├── docs/                  # Documentation
└── docker-compose.yml     # Root orchestrator
```

### Network Architecture
- **Single Network**: `zoi-network` for all inter-service communication
- **Port Scheme**: 70XX for core services, 72XX for platform, 73XX for tools
- **Service Discovery**: Docker DNS resolution within network
- **External Access**: Traefik reverse proxy with domain routing

## 🔧 Development Conventions

### File Organization
- **Centralized Configs**: All service configs in `config/` directory
- **Stack Separation**: Each app has its own `docker-compose.yml`
- **Environment Variables**: `.env` file for customization
- **Documentation**: README.md in each app directory

### Naming Conventions
```yaml
Services:
  - Container names: lowercase, descriptive (e.g., 'litellm', 'qdrant')
  - Network: 'zoi-network' (shared across all services)
  - Volumes: service-name-data (e.g., 'postgres-data', 'qdrant-data')

Ports:
  - Core AI: 7000-7099 (LiteLLM: 7010, Ollama: 7040, etc.)
  - Platform: 7200-7299 (MongoDB: 7202, Authentik: 7208)
  - Tools: 7300-7399 (n8n: 7300, OpenWebUI: 7301)
  - Knowledge: 7080-7089 (Archon services)

Configuration:
  - YAML preferred for complex configs
  - Environment variables for simple settings
  - Secrets via environment variables, not hardcoded
```

### Docker Compose Patterns
```yaml
# Standard service template
service-name:
  image: official/image:tag
  container_name: service-name
  ports:
    - "${SERVICE_PORT:-default}:internal_port"
  environment:
    - KEY=value
    - SECRET=${ENV_VAR}
  volumes:
    - service-data:/data/path
    - ../../config/service:/config:ro
  networks: [zoi-network]
  restart: unless-stopped
  depends_on: [dependency-service]
  healthcheck:
    test: ["CMD", "health-check-command"]
    interval: 30s
    timeout: 10s
    retries: 3
```

## 🤖 AI Services Context

### LiteLLM Gateway (Port 7010)
- **Purpose**: Unified API gateway for 18+ AI models
- **Config**: `config/litellm/config.yaml` (centralized)
- **Features**: Auto-routing, caching, usage tracking, vector integration
- **API**: OpenAI-compatible endpoints (`/v1/chat/completions`, `/v1/embeddings`)
- **Authentication**: Bearer token with master key

### Vector Database (Qdrant - Port 7060)
- **Collections**: 8 specialized collections for different use cases
- **Integration**: Embedded in LiteLLM for RAG functionality
- **Models**: RAG-enhanced models (`zoi-rag-helper`, `zoi-rag-thinker`)
- **Embeddings**: 1024-dimensional vectors via `zoi-embed` model

### Model Serving
- **vLLM** (Port 7050): High-performance inference (Qwen2.5-Coder-7B)
- **Ollama** (Port 7040): Local model management (Qwen2.5-7B variants)
- **Auto-routing**: Intelligent model selection based on query type

## 📋 Common Code Patterns

### Docker Compose Service Template
```yaml
service-name:
  image: official/image:latest
  container_name: service-name
  restart: unless-stopped
  ports:
    - "${SERVICE_PORT:-default}:internal"
  environment:
    - CONFIG_VAR=${ENV_VAR}
    - DATABASE_URL=postgresql://user:pass@postgres:5432/db
  volumes:
    - service-data:/app/data
    - ../../config/service:/config:ro
  networks: [zoi-network]
  depends_on:
    - postgres
    - redis
  healthcheck:
    test: ["CMD-SHELL", "curl -f http://localhost:port/health"]
    interval: 30s
    timeout: 10s
    retries: 3
  labels:
    - "traefik.enable=true"
    - "traefik.http.routers.service.rule=Host(`service.${DOMAIN}`)"
```

### Configuration File Patterns
```yaml
# Standard YAML config structure
service_config:
  # Core settings
  host: "0.0.0.0"
  port: 8080

  # Database connection
  database:
    url: "${DATABASE_URL}"
    pool_size: 10

  # External service integration
  integrations:
    litellm:
      base_url: "http://litellm:4000"
      api_key: "${LITELLM_API_KEY}"

  # Feature flags
  features:
    enable_auth: true
    enable_logging: true
```

## 💡 AI Agent Guidelines

### When Modifying This Codebase:

#### 🏗️ **Architecture Principles**
1. **Microservices First**: Each service should be independently deployable
2. **Configuration as Code**: All settings in version-controlled files
3. **Network Isolation**: Services communicate via `zoi-network` only
4. **Stateless Design**: Store state in databases, not containers

#### 🔧 **Development Standards**
1. **Centralized Configs**: Always use `config/` directory for service settings
2. **Environment Variables**: Use `.env` for customizable values
3. **Health Checks**: Every service must have health check endpoints
4. **Graceful Degradation**: Services should handle dependency failures

#### 📝 **Code Quality**
1. **Documentation**: Update README files when adding features
2. **Naming Conventions**: Follow established patterns for consistency
3. **Error Handling**: Implement comprehensive error handling and logging
4. **Security**: Never hardcode secrets, use environment variables

#### 🧪 **Testing Approach**
1. **Local Testing**: Verify changes work in development environment
2. **Integration Testing**: Test service interactions after changes
3. **Performance Testing**: Monitor resource usage after modifications
4. **Rollback Plan**: Always have a way to revert changes

#### 🚀 **Deployment Practices**
1. **Staged Rollout**: Test in development before production
2. **Service Dependencies**: Understand and respect startup order
3. **Monitoring**: Check service health after deployments
4. **Documentation**: Update deployment guides for new features

This ecosystem is **production-grade** and serves **enterprise workloads**. Maintain these standards to ensure reliability, security, and maintainability.
